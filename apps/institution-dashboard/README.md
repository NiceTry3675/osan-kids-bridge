# 운영기관용 수요 기반 추천 대시보드(목업)

보호자들이 익명으로 남긴 "아이가 참여할 수 있는 시간·동네" 수요를 모아, 운영기관이 프로그램을 열 때 가장 많은 가정이 참여할 수 있는 요일·시간대·장소 조합을 추천하는 기관용 화면입니다. 이번 단계는 백엔드 없이 **합성 데이터로만 동작하는 목업**입니다. 계획과 결정 사항은 [기능2 계획서](../../docs/feature2-institution-dashboard-plan.md)를 따릅니다.

보호자 웹과 기관 대시보드는 같은 서비스의 두 화면입니다. 색상·글꼴·화면 언어 고르기는 [`packages/ui`](../../packages/ui)를 함께 씁니다. 보호자 웹의 검색 조건은 현재 기관 화면으로 전송되지 않으며, 실제 익명 수요 수집에는 별도의 선택 동의와 집계 API가 필요합니다.

## 로컬 실행

```bash
npm install          # 저장소 맨 위에서 한 번
npm run dev:dashboard
```

데스크톱에서는 조건 패널이 왼쪽에 늘 보이고, 폭 900px 아래(태블릿·휴대폰)에서는 조건을 접은 채 결과를 먼저 보여 줍니다. `npm run build`로 타입 검사와 배포용 빌드를, `npm test`로 시간 변환·합성 데이터·집계 억제·추천 로직을 확인합니다. 머리말의 언어 버튼에서 쉬운 한국어·베트남어·중국어를 검색해 선택할 수 있습니다. 두 화면은 `packages/ui/LanguageSelector.tsx`의 선택창을 함께 씁니다. 베트남어와 중국어 문구는 검수 전 초안이라 공개 빌드에서는 고를 수 없고 개발·시연 빌드에서만 열립니다(보호자 웹과 같은 정책).

## 화면 (유저플로우 v3, 7화면)

하단 탭 3개(수요·추천·안내)와 그 위에 여는 시트로 구성합니다. 넓은 화면에서는 탭이 위로 가고, 추천 조건과 결과를 나란히 보여 줍니다. 그림은 `docs/userflow/admin.html`(폴더의 `운영기관_유저플로우_v3.png`).

| 번호 | 화면 | 종류 | 하는 일 |
|---|---|---|---|
| 01 | 수요 현황 | 탭 | 핵심 숫자, 요일×시간대 히트맵, 동별·언어·한국어 수준 분포 |
| 02 | 조건 고르기 | 시트(휴대폰) | 동·학년·분야·사용 언어 |
| 03 | 작은 집계 가림 | 수요 탭의 상태 | 5 미만·가림, 대상 5가정 미만이면 결과 없음 |
| 04 | 추천 조건 | 탭 | 분야 타일·학년·정원·반 수, 후보 장소·기존 계획은 펼쳐서 |
| 05 | 추천 결과 | 추천 탭 | 1~3안, 닿는 가정·비율, 기존 계획 비교, 반별 내역·정원 초과 |
| 06 | 추천 자세히 | 시트 | 시간표(추천·기존 칸), 언어·한국어 수준, 준비 제안과 이유 |
| 07 | 데이터 안내 | 탭 | 사용 항목·모으지 않는 항목·표시 기준·다음 단계 |

## 데이터는 모두 가상입니다

- 모든 숫자는 브라우저에서 고정 시드로 만든 합성 응답 400가정(`src/data/generate.ts`)에서 나옵니다. 새로고침해도 같은 결과가 나오며 실제 보호자 응답·실제 통계가 아닙니다.
- 후보 장소(`src/data/venues.ts`)는 "가상 ○○동 도서관"처럼 실제 시설로 오해하지 않을 이름과 지어낸 대관 가능 칸을 씁니다.
- 이름·연락처·정확한 주소·출신국 항목은 데이터 구조에 없습니다. 출신국 대신 보호자 웹의 화면 언어만 씁니다.

## 가정은 한 파일에 있습니다

동별 가구 비율, 동 인접 관계(2열 × 3행 격자로 단순화), 칸별 인기 가중치, 화면 언어 비율, 한국어 수준 응답률과 분포, 학년·관심 분야 분포, 시간대 경계(06·12·18·22시)와 겹침 기준(30분), 소수 셀 억제 기준(5), 정확 탐색 한도(조합 200만 개), 신청 전환율, 반당 정원 범위, 수업 제안 규칙, 시연 기본 입력(기존 계획 포함)은 모두 `src/data/assumptions.ts`에 "시연용 가정"으로 표시해 모았습니다. 휴대폰의 데이터 안내 화면에는 사용 항목과 표시 기준을 요약했습니다. 실제와 맞는지는 팀 확인이 필요합니다.

## 구조

- `src/types.ts`: 데이터 항목 초안 v0.2 타입과 장소·프로그램 조건·추천 결과 타입
- `src/lib/slots.ts`: 21칸 정의와 `toSlots`. 보호자 웹의 자유 시간 범위(`AvailableWindow`)를 21칸으로 바꿉니다. 모든 범위에 같은 기준(칸과 30분 이상 겹침)을 써서 범위를 넓히면 칸이 늘기만 하고, 06~22시 안의 60분 이상 범위는 늘 1칸 이상이 됩니다. 보호자 웹은 1분짜리 범위도 받으므로, 30분보다 짧거나 대부분 06~22시 밖인 범위는 빈 배열이 될 수 있습니다. 실제 연결 때는 저장 전에 걸러 보호자에게 다시 물어야 합니다. 날짜는 시간대와 무관하게 달력 날짜 그대로 요일을 구합니다.
- `src/lib/aggregate.ts`: 필터와 집계, 소수 셀 억제. 1~4가정은 "5 미만"으로 가리고 0은 그대로 둡니다. 대상이 5가정 미만이면 숫자를 하나도 내보내지 않습니다. 합계와 함께 보이는 분포는 `suppressPartition`으로 보조 억제를 합니다(아래 개인정보 절).
- `src/lib/recommend.ts`: 최대 커버리지 추천. 선택지 = (칸, 장소), 가정이 선택지에 닿으려면 그 칸이 가정의 가능 칸이고 장소의 동이 같은 동 또는 인접 동이어야 합니다. 같은 칸·같은 동의 장소는 닿는 가정이 같으므로 묶어서 따지고, 조합 수가 200만 개 이하이면 비트셋으로 전부 비교합니다. 반 수만큼 서로 다른 묶음을 고르는 조합에 더해, 더 적은 묶음을 고르고 남는 반을 같은 시간·같은 동의 다른 장소나 닿는 가정이 없는 선택지로 채우는 조합도 따지므로, 1~3위는 "서로 다른 (칸, 장소) k개로 만들 수 있는 모든 조합 중 닿는 가정 집합이 서로 다른 상위 3개"와 같습니다(테스트가 제한 없는 무차별 대입과 비교). 넘으면 탐욕 알고리즘으로 대체하고 화면에 표시합니다. 결과는 UI와 분리된 순수 함수입니다.
- `src/components/`: 화면 구성요소(차트 라이브러리 없이 CSS로 그림)
- `src/testing/disclosure.ts`: 테스트 전용 역산 점검 도구(앱 번들에 들어가지 않음)

## 탐욕 대체는 지금 시연에서 나오지 않습니다

묶음은 (칸, 동) 쌍이라 장소가 늘어도 최대 6동 × 21칸 = 126개이고 반은 최대 3개라, 따질 조합은 많아야 333,501개(126C3 + 126C2 + 126)로 한도 200만 개보다 작습니다. 그래서 화면에서는 늘 정확 탐색이 돌고, 탐욕 대체는 동·칸·반 수가 늘어나는 나중 입력을 위한 장치입니다. 발표에서 보여 주려면 주소 뒤에 `?comboLimit=0`을 붙여 한도를 낮추면 "탐욕 알고리즘(근사)" 표시와 안내가 나옵니다.

## 개인정보 보호 장치와 남은 한계

- 1~4가정인 집계 칸은 "5 미만"으로 가립니다(히트맵·동별·화면 언어·한국어 수준·추천 카드).
- 합계와 함께 보이는 분포(수요 현황의 동별·화면 언어·한국어 수준, 추천 카드의 화면 언어·한국어 수준, 3개 반 카드의 2·3반 "새로 더함")는 합계에서 보이는 칸을 빼서 가린 칸 값이 정해지면, 0이 아닌 가장 작은 칸(같은 값 모두)을 함께 가리고 가린 칸을 모두 "가림"으로 표시합니다. 합계가 칸 수 × 4(또는 칸 수)와 같으면 값과 상관없이 분포 전체를 가립니다. 테스트는 수요 현황의 모든 필터 조합(동 부분집합 64개 포함)과 추천 카드 1만여 장에서, 규칙까지 아는 사람이 같은 화면을 만드는 원래 값을 모두 따져도 1~4 칸이 하나로 정해지지 않는지 확인합니다.
- 비율(%)·가정당 평균 칸 수·통역/수업 제안 문장은 억제를 거친 숫자로만 계산합니다. 미응답이 가려지면 한국어 수준 응답률과 미응답 %는 표시하지 않고, 가정당 평균은 가린 히트맵 칸을 2.5로 어림합니다.
- 남은 한계(실제 서비스에서 서버가 정할 것)
  - 2개 반 카드의 2반 "새로 더함"과 설명 속 "더 모은 가정"은 "닿는 가정 합계 − 1반"이라 화면의 두 숫자로 계산됩니다. 가능 시간·동만 담긴 숫자라 그대로 두되, 설명 문장은 1~4일 때 숫자 없이 씁니다. 3반이 새로 더하는 가정이 0인 카드도 같습니다. 3개 반에서 2·3반을 함께 가려도 반 순서(새로 더하는 가정이 많은 순)를 알면 합이 6일 때처럼 드물게 좁혀질 수 있습니다.
  - 반별 예상 인원은 모형 값(닿는 가정 몫 × 40%)이라 1~4명만 "5명 미만"으로 가리고, 반당 정원은 5명부터 받습니다.
  - 필터를 조금씩 바꾼 여러 화면을 비교해 차이로 알아내는 공격은 화면 하나 안에서 막을 수 없습니다. 실제 서버 집계(`GET /demand/aggregate`)에서 조회 조건 제한이나 잡음 추가 같은 보호 규칙을 함께 정해야 합니다.

## 팀과 확인할 것

- 동 인접 관계와 동별 가구 비율 가정이 실제와 크게 어긋나지 않는지
- 오전·오후·저녁 경계 시각(06·12·18·22시)과 30분 겹침 기준
- 한국어 수준 3단계가 자녀 기준인지 보호자 기준인지(목업은 자녀 기준)
- 데이터 항목 초안 v0.2가 바뀌면 `src/types.ts`와 `src/data/generate.ts`를 함께 바꿀 것

## 실제 서비스로 넘어갈 때(이번에 만들지 않음)

보호자 웹에 "희망 시간을 익명으로 기관에 알려 주기" 동의 단계를 추가해 `POST /demand`로 보내고, 서버가 `toSlots`로 21칸 변환해 저장하며(빈 결과면 저장하지 않고 다시 묻기), 대시보드는 `GET /demand/aggregate`처럼 이미 집계·억제된 숫자만 받습니다. 이 목업의 `suppressPartition` 규칙을 서버 집계에 옮기고, 여러 조회를 비교하는 공격에 대한 보호 규칙을 함께 정해야 합니다.
