# 기능2 운영기관용 AI 추천 대시보드: 목업 계획

담당: 준현 · 작성일: 2026-10-14 · 상태: 목업 단계 계획

## 1. 한 줄 요약

보호자들이 익명으로 남긴 "아이가 참여할 수 있는 시간·동네" 수요를 모아, 운영기관이 프로그램을 열 때 **가장 많은 가정이 참여할 수 있는 요일·시간대·장소 조합**을 추천하는 기관용 대시보드입니다. 이번 단계는 백엔드 없이 **합성 데이터로 동작하는 목업**만 만듭니다.

경기도 이주민 포털 등은 이미 프로그램 안내·번역을 제공하므로, 우리 서비스의 차별점은 이 "수요 기반 일정·장소 추천"입니다.

## 2. 이번 범위에서 정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 데이터 | 브라우저에서 고정 시드로 만드는 합성 수요 데이터만 사용 | 준현 결정(목업만). 실제 수집 경로는 발표에서 설명 |
| 코드 위치 | `apps/institution-dashboard` 별도 앱 | 보호자 웹 담당과 파일 충돌이 없음. 추천 로직은 UI와 분리된 순수 모듈 |
| 기술 | 보호자 웹과 같은 Vite + React 19 + TypeScript + Vitest, 차트 라이브러리 없이 CSS로 그림 | 팀 전체가 같은 도구를 쓰고 의존성을 늘리지 않음 |
| 화면 | 데스크톱 우선, 태블릿 폭까지 반응형 | 기관 담당자는 PC에서 봄 |
| 시간 단위 | 7요일 × 오전/오후/저녁 21칸 격자 | 데이터 항목 초안 v0.2 |

| 로그인·백엔드·배포 | 하지 않음 | 목업 범위 밖 |

## 3. 합성 수요 데이터

한 건은 "보호자 한 가정이 익명으로 남긴 희망 조건"입니다. 데이터 항목 초안 v0.2를 따릅니다.

```ts
type Dong = '중앙동' | '대원동' | '남촌동' | '신장동' | '세마동' | '초평동'
type Weekday = 'mon' | 'tue' | 'wed' | 'thu' | 'fri' | 'sat' | 'sun'
type DayPart = 'morning' | 'afternoon' | 'evening'   // 오전 06~12시, 오후 12~18시, 저녁 18~22시
type SlotKey = `${Weekday}-${DayPart}`               // 21칸
type Interest = 'experience_culture' | 'korean_study' | 'sports_arts' | 'career'  // 보호자 웹과 동일
type KoreanLevel = 'beginner' | 'intermediate' | 'fluent'   // 자녀 한국어 수준, 선택 항목
type ScreenLanguage = 'ko-easy' | 'vi' | 'zh'                // 보호자 웹의 화면 언어

interface DemandResponse {
  id: string
  dong: Dong
  child_grade: 1 | 2 | 3 | 4 | 5 | 6
  available_slots: SlotKey[]      // 1칸 이상
  interests: Interest[]           // 0개 이상
  korean_level?: KoreanLevel      // 선택이므로 비어 있을 수 있음
  screen_language: ScreenLanguage
}
```

수집하지 않는 것: 이름, 연락처, 정확한 주소, 출신국. 출신국 대신 화면 언어만 씁니다.

생성 규칙(시연용 가정, 실제 통계 아님):
- 고정 시드 PRNG로 약 400건을 만들어 새로고침해도 같은 결과가 나옵니다.
- 맞벌이 가정을 가정해 평일 저녁과 토요일 오전·오후에 수요가 몰리고, 평일 오전은 적게 둡니다.
- 동별 가구 수, 화면 언어 비율, 한국어 수준 응답률은 `src/data/assumptions.ts` 한 파일에 모아 두고 "시연용 가정"이라고 표시합니다.

## 4. 이동 범위와 후보 장소

- 보호자는 "같은 동 또는 인접한 동"의 장소까지 갈 수 있다고 가정합니다. 동 인접 관계는 `assumptions.ts`의 표 하나로 두고, 실제 지도와 맞는지 팀이 확인해야 할 항목으로 남깁니다.
- 기관은 후보 장소를 고릅니다. 시연용 장소는 "가상 ○○동 도서관"처럼 실제 시설로 오해하지 않을 이름을 쓰고, 장소마다 대관 가능한 칸(21칸 중 일부)을 둡니다.

## 5. 추천 로직

입력(기관이 화면에서 정함)
- 프로그램 분야(4개 중 하나 또는 전체), 대상 학년 범위
- 열 반 수 k(1~3), 반당 정원
- 사용할 후보 장소(복수 선택)
- 비교할 기존 계획(선택): 추천과 같은 반 수의 (칸, 장소). 예를 들어 반 3개를 모두 "토요일 오전"에 가상 중앙동 도서관·세마동 복합문화센터·남촌동 작은도서관에서 여는 관행

대상 수요: 학년이 범위 안이고, 분야를 정했다면 관심 분야에 그 분야가 있거나 관심 분야를 비워 둔 응답.

선택지 하나 = (요일·시간대 칸, 장소). 그 칸이 장소의 대관 가능 칸이어야 합니다.
한 가정이 선택지에 "닿는다" = 그 칸이 가정의 가능 칸에 있고, 장소의 동이 가정의 이동 범위에 있음.

목표: k개 선택지를 골라 **적어도 하나에 닿는 가정 수(커버리지)를 최대화**합니다(최대 커버리지 문제).
- 경우의 수가 작으면(조합 200만 개 이하) 비트셋으로 전부 따져 정확한 상위 3개 조합을 냅니다.
- 그보다 크면 탐욕 알고리즘(이론상 최적의 약 63% 이상 보장)으로 대체하고 화면에 그 사실을 표시합니다.
- 같은 칸·같은 장소를 두 번 고르지 않습니다.

출력(추천 카드 1~3위)
- 커버리지: "대상 수요 212가정 중 131가정(62%)"
- 반별 내역: 각 반이 새로 더하는 가정 수, 반별 예상 인원이 정원을 넘으면 "정원 초과 예상, 반 추가 고려"
- 참여 가정의 화면 언어 분포 → "베트남어 안내 필요 38가정" 같은 통역·번역 준비 제안
- 한국어 수준 분포 → 수업 난이도·보조교사 제안
- 기존 계획과 비교: "기존 계획 24% → 추천 62%"
- 왜 이 조합인지 한두 문장 설명(규칙 기반 문장, 외부 LLM 호출 없음)

## 6. 개인정보 보호 장치

- 대시보드는 개별 응답을 절대 보여 주지 않고 집계만 보여 줍니다.
- 집계 칸이 1~4가정이면 숫자 대신 "5 미만"으로 가립니다(소수 셀 억제). 히트맵·동별 막대·언어 분포 모두 적용합니다.
- 합계와 함께 보이는 분포(동별·화면 언어·한국어 수준)는 합계에서 빼서 가린 칸을 알아낼 수 있으면 다른 칸도 함께 "가림"으로 가립니다(보조 억제). 비율(%)·평균·제안 문장은 화면에 보이는(억제를 거친) 숫자로만 계산합니다.
- 필터를 많이 걸어 대상이 5가정 미만이 되면 결과 대신 "조건을 넓혀 주세요"를 띄웁니다.

## 7. 화면 구성

1. **수요 현황**: 동·학년·관심 분야·화면 언어 필터, 핵심 숫자(응답 가정 수 등), 요일×시간대 히트맵, 동별 수요 막대, 화면 언어·한국어 수준 분포.
2. **일정·장소 추천**: 왼쪽에 프로그램 조건 입력, 오른쪽에 추천 1~3위 카드와 기존 계획 비교. 추천 칸은 히트맵 위에 표시.
3. **데이터 안내**: 무엇을 모으고 무엇을 모으지 않는지, 합성 데이터와 가정 목록, 실제 서비스에서의 수집 경로(보호자 웹의 익명 동의 단계, 아래 8절).

## 8. 실제 서비스로 넘어갈 때(이번에 만들지 않음)

- 보호자 웹에 "희망 시간을 익명으로 기관에 알려 주기" 동의 단계를 추가하고 `POST /demand`로 보냄. 검색 조건을 몰래 기록하지 않습니다.
- 서버가 자유 시간 범위를 21칸으로 변환해 저장(이번에 만드는 변환 함수 재사용). 변환 결과가 0칸이면(30분 미만 범위 등) 저장하지 않고 다시 묻습니다.
- 기관 대시보드는 `GET /demand/aggregate`처럼 이미 집계·억제된 숫자만 받음.

## 9. 작업 순서

1. 앱 뼈대, 타입, 가정 파일, 합성 데이터 생성기와 테스트
2. 집계(소수 셀 억제 포함)와 수요 현황 화면
3. 추천 로직(정확 탐색·탐욕 대체)과 무차별 대입 비교 테스트
4. 일정·장소 추천 화면, 기존 계획 비교
5. 데이터 안내 화면, README, 시연 동선 점검
